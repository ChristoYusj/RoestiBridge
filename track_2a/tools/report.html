Technical report: RöstiBridge

  • Track: Track 2A, UZH: Detecting Cross-Lingual Semantic Differences in Swiss Government Websites
  • Event: Online
  • Team: RedPandas: Christopher Yazigi, Giovanni Yazbeck, Alfredo Pio Yazbeck
  • Demo: Firefox extension in src/extension (dist/roestibridge-0.1.5.xpi); screenshots in docs/

1. Summary

Swiss authorities publish the same page in up to four languages, and the versions do not always say the same thing: sentences are dropped, numbers or deadlines change, or “must” becomes “may”. RöstiBridge, a bridge over the Röstigraben, brings token-level recognition of semantic differences (RSD) to the reader. It is a Firefox extension that highlights passages of an official page (federal, cantonal, RTS news, or a parliamentary PDF) whose meaning may differ from the reference language version. Hovering a highlight shows the other version's excerpt as a citation and an Apertus explanation, in the reader's chosen language.

The same single Apertus prompt is benchmarked on SwissGov-RSD [1]. Apertus-v1.5-70B reports difference spans, which are projected onto tokens; 3-sample self-consistency averages them. On a 120-document dev subset this gives a macro token-level Spearman of 0.131, against 0.083 for a model-free number-mismatch baseline and 0.096 for the raw single-sample spans. Test-split predictions (168 documents) are in predictions/test_70b_n3/.

  • Federal vs. cantonal logic (shared/sites.js):
    • Federal domains are compared with FR and DE (whichever the page is not in).
    • Bilingual cantons (BE/FR/VS/GR) are compared with the other official language.
    • Monolingual cantons are compared with their official language.
  • Only real differences are shown: a reported difference whose two excerpts are the same string, or whose “missing” text does appear in the other version (place names, datelines, numbers, acronyms), is dropped before display. The cache is versioned, so a change to this filtering never serves stale results.
  • Explanations in the reader's language (EN / DE / FR / IT, set in the options): the request states the explanation language explicitly, and “TEXT A / TEXT B” in Apertus' answer become “the French version”, “die deutsche Fassung”, etc. For English the request stays byte-identical to the frozen benchmark prompt.
  • Robustness: every Apertus request has a 120 s timeout and 3 retries. Each section of a page is checked on its own, so one slow answer never discards the others; only complete results are cached. The status pill reports per language version how many differences were highlighted, and the options page tests the key when you save it.
  • Key handling: the API key lives in browser.storage.local and is only read by the background script. Page scripts never receive it.
  • Benchmark pipeline (src/roestibridge): a stdlib-only Python client (llm.py), span → token projection (rsd.py), the metric (metrics.py, a faithful re-implementation of the official evaluate_predictions_admin.py pooling) and a CLI. It reads the same prompt.json as the extension, and a unit test enforces this.

3. Use of Apertus

  • Model: swiss-ai/Apertus-v1.5-70B (CSCS-hosted, OpenAI-compatible endpoint). Apertus-v1.5-8B can be selected in the options for on-prem use.
  • How it is used: prompting-only inference with JSON output (response_format: json_object, with a fallback when the endpoint does not support it). Apertus is used for:
    1. difference detection with severity and explanation (core RSD);
    2. matching translated URL slugs on the new admin.ch CMS;
    3. turning an RTS headline into German search queries and deciding whether an SRF article is the same story;
    4. picking the translated sibling of a parliamentary document.
  • Prompt: src/extension/shared/prompt.json (rb-prompt-v1). The system prompt defines what counts as a difference (omission/addition, numbers/dates, obligation/scope, legal terms, actionable nuance) and what does not (grammar, word order, free translation). It asks for exact, short excerpts.
  • Benchmark settings: temperature 0 for the first sample and 0.7 for samples 2–3, max_tokens 2000, one call per document pair. Token usage (from the API) is about 0.82M prompt and 0.25M completion tokens for the 3-sample test run (raw_*.jsonl → usage).
  • No other model is used anywhere in the pipeline or for evaluation.

Example answer (dev document admin_fr_32, EN ↔ FR, severity 4, type number|scope): the English “Each year about 1,700 A4 pages of text are translated into Romansh.” is matched with the French “… quelque 1700 pages A4 sont traduites en romanche, deux tiers d'entre elles étant confiées à la Chancellerie d'État des Grisons”; Apertus explains that the French version adds where two thirds of the work goes.

4. Data

  • SwissGov-RSD [1] (ZurichNLP/SwissGov-RSD on Hugging Face) is downloaded at run time into data/swissgov-rsd/ and is not committed.
  • Development used a deterministic, evenly spaced 40-document subset of the dev split per language (--limit 40, 120 pairs) to stay within the API budget.
  • The test split was never evaluated or inspected: evaluate --split test exits with an error. Test predictions were produced once with the prompt and post-processing frozen on dev.
  • The extension processes public government pages on the fly and stores nothing beyond a local cache of model answers.
  • The dataset's DE/FR/IT texts contain U+FFFD replacement characters in place of accented letters (e.g. L�approvisionnement). The prompt tells the model to copy excerpts verbatim “even if characters look garbled”, and the projection treats � as a word character.

5. Evaluation

Metric: the official one. For each language pair, all tokens of side A and side B with gold ≠ −1 are pooled (predictions are padded or truncated to the gold length), global Spearman is computed, and the macro average is taken over EN–DE/FR/IT. Our implementation matches scipy.stats.spearmanr on the pooled vectors.

Error analysis (FR, 1 sample):

  • Precision is the lever. Of the tokens we mark, 226 are true positives and 1,752 are false positives. Apertus over-reports “different wording, same meaning” spans at low severity, which motivated the severity ≥ 2 cut. Many missed gold differences (1,119 tokens) are small structural omissions such as link labels and list items.
  • Span projection is reliable: 376 of 382 returned excerpts were located in the token sequence.
  • FR is the hardest pair. The FR documents are longer (461 vs 363 tokens on average for DE) and the FR texts carry the most � corruption.

6. Limitations

  • Document-level RSD is hard for prompted LLMs, consistent with [1]. The dev subset is small (120 pairs), so the post-processing choices may be slightly overfit.
  • Extension chunk alignment is proportional (± 4 blocks). When a page has very different structures across languages, content outside the window can be reported as “missing”. When Apertus quotes the wrong side or paraphrases, the locator tries the other excerpt and the first or last six words of the quote.
  • Counterpart discovery depends on site conventions. The admin.ch slug matcher needs both homepages to list the page. RTS→SRF uses a news search (Bing News RSS, DuckDuckGo fallback), and SRF is independent journalism, not a translation: differences there are coverage differences, not translation errors.
  • Language metadata: OpenParlData labels some French parlament.ch documents as it, so Apertus picks the sibling by title rather than by the language field.
  • Packaging: the extension is unsigned (temporary add-on) and uses Manifest V2 for blocking webRequest (PDF interception).

7. Reproducibility

  • make run (Docker, no GPU) runs four steps:
    1. the 12 unit tests;
    2. re-scoring of the shipped raw Apertus outputs for dev (exactly the numbers above, no API needed);
    3. the model-free baseline;
    4. rebuilding the submitted test predictions from the shipped raw outputs.
    With LLM_API_KEY set it also runs a live Apertus prediction and evaluation on LIVE_LIMIT dev documents per language.
  • make predict-test regenerates the test predictions (168 × 3 calls).
  • Apertus output at temperature 0 is not perfectly deterministic on the hosted endpoint. That is why the raw responses are shipped and all scores are recomputed from them.

8. Next steps

  • Sentence alignment before prompting. Align with the LLM or embeddings, then ask per aligned pair. This should improve both recall and the “missing” false positives.
  • Calibrate severities per language on dev.
  • Try 8B with more samples for an on-prem budget.
  • Ship a signed MV3 build: declarativeNetRequest for PDFs, plus a “report this discrepancy to the authority” button that drafts a correction request with the citation.
